# 안내 우선 코파일럿 / Guidance-First Copilot ("자비스 모드" 재검토) (설계)

> 상태: **비전/설계 문서 (구현 전)**. 로드맵 **M7**에 대응.
>
> **개정 이력:** 초안은 "무엇을 원하는지 묻고 **대신 화면을 조작**해주는" 자율 대행
> 비서(자비스)를 목표로 삼았다. 근거 검증([evidence.md](evidence.md), [backlog.md](backlog.md)
> Epic C 참고) 결과 그 형태는 이 사용자군에게 **안전하게 성립하지 않는다**고 판단하여,
> 범위를 **안내 우선(guidance-first) + 사용자가 개시하는 좁은 되돌릴 수 있는 자동화**로
> 축소·재정의했다. 아래 §0이 그 이유이고, §1 이후가 재정의된 설계다.

## 0. 왜 "자율 대행"에서 물러나는가 (검증 결과)

핵심 반증은 하나다: **이 사용자군은 AI가 만든 오류를 약 50%만 잡아낸다.**
(Hong & Kacorri, *"Blind Users' Trust and Verification of AI-Generated Image
Descriptions"*, ASSETS 2024 — 문맥·수치는 [evidence.md](evidence.md).)

"에이전트가 조작하고, 사용자가 감독하며, 위험할 때만 확인한다"는 초안 모델은
**감독과 확인이 신뢰할 수 있다**는 가정 위에 서 있다. 그런데 화면을 못 보는 사용자는:

- 에이전트가 **엉뚱한 대상을 클릭했는지** 스스로 검증할 수 없다(grounding 오류를
  잡을 시각 채널이 없다). 검증기(LLM)도 같은 화면을 같은 한계로 본다 — 오류의 상관.
- "확인하시겠어요?" 대화상자조차, **무엇을 확인하는지**의 설명이 곧 AI 생성물이라
  같은 50% 오류율의 지배를 받는다. 잘못된 전제를 확인당하는 위험.
- 되돌릴 수 없는 행동(결제·삭제·전송)에서 오조작 1회의 비용이 비대칭적으로 크다.

따라서 "AI가 행동의 주체, 사람이 감독자"라는 축은 이 사용자군에서 **안전 마진이
음수**다. 방어 가능한 축은 반대다:

> **사람이 행동의 주체, AI가 눈·안내자.** AI는 화면을 **풍부하게 설명**하고, 다음
> **안전한 행동을 이름으로 지목**하며(“'로그인' 버튼은 우측 상단에 있습니다”),
> **최종 실행 키는 사용자가 누른다.** 자동화는 사용자가 명시적으로 개시한, **알려진·
> 되돌릴 수 있는** 행동에 한해 좁게 허용한다(Savant 모델).

이 재정의는 겁이 아니라 **역할 배치**다. 자율 대행을 영구히 버리는 게 아니라, 이
사용자군에서 안전을 실증(사용자 테스트, [user-testing.md](user-testing.md))하기 전까지
**기본값을 안내로 두는** 것이다.

## 1. 무엇을 만드나 (재정의된 범위)

빛길은 이미 "무엇이 보이나"를 설명한다. 안내 우선 코파일럿은 그 위에 **"그래서
지금 무엇을, 어떻게 하면 되나"**를 얹는다 — 조작을 대신 하지 않고, **손을 잡아
이끈다.**

| | 지금 (해설자) | 목표 (안내자 + 좁은 자동화) |
|---|---|---|
| 입력 | 화면 프레임 | 프레임 + **음성 질문/의도**("로그인 어떻게 해?") |
| 판단 | "무엇이 보이나" | "무엇이 보이나 → **다음 안전한 한 수는 무엇인가**" |
| 출력 | 설명 | 설명 + **다음 행동 지목**(위치·레이블·단축키) |
| 실행 | 없음 | **사용자가 키를 누름.** 좁은 자동화만 사용자 개시로 대행 |
| 사람 역할 | 듣고 스스로 조작 | 듣고 **안내받아** 조작 — 주도권은 사람 |

## 2. 상호작용 루프 (안내 루프)

```
[의도 청취]  음성 STT → 목표/질문 파악 / 모호하면 되묻기
     ↓            "로그인하고 싶어" / "이 팝업 뭐야?"
[화면 이해]   현재 화면을 읽어 관련 요소를 구조적으로 파악
     ↓
[안내 생성]   다음 안전한 한 수를 이름·위치·단축키로 지목
     ↓            "우측 상단 '로그인' 버튼입니다. Tab 3번 후 Enter로 갈 수 있어요."
[사용자 실행] 사용자가 직접 키를 누름 (기본). 또는 —
     ↓            사용자가 "대신 눌러줘"라고 명시 개시 & 행동이 되돌릴 수 있으면
[좁은 자동화]  화이트리스트·되돌림 가능 행동에 한해 1스텝 대행 → 즉시 보고
     ↓
[확인/검증]   무엇을 했고 지금 무엇이 보이는지 낭독 → 사용자가 다음을 판단
     ↺  목표까지 반복 / 어느 시점이든 사용자가 멈출 수 있음
```

초안의 "계획 → 자동 실행 → 검증 → 재계획" 자율 루프와의 차이: **실행 주체가
사용자**이고, 자동화는 루프의 기본이 아니라 **사용자가 매번 개시하는 예외**다.

## 3. 설계 요소

### A. 의도 세션 (IntentSession)
음성 요청을 목표/질문으로 유지하고, 모호하면 되묻는다. 다단계 대화를 하나의 맥락으로
묶는다. `GoalTracker`(이미 존재)를 세션 목표 보유자로 확장. **행동을 자동 개시하지
않는다** — 사용자의 다음 발화/키 입력을 기다린다.

### B. 안내기 (Advisor) — 초안의 "계획기"를 대체
목표 + 현재 화면 → **다음 한 수의 안내 텍스트**를 생성. 여러 스텝을 미리 자동
실행하려고 분해하지 않는다. 대신 "지금 할 한 가지"를 위치·레이블·키보드 경로로
알려주고, 사용자가 그것을 한 뒤 다시 화면을 읽어 다음을 안내한다. 안내는 **화면에
실제로 보이는 요소만** 지목한다(없는 버튼을 지어내지 않음 — Epic A 반날조 원칙).

### C. 좁은 자동화 (BoundedAutomator) — 초안의 "행동 실행기"를 축소
자동화를 **완전히 버리지는 않되**, 다음 3조건을 **모두** 만족할 때만 1스텝 대행한다:

1. **사용자가 명시적으로 개시**했다("이거 눌러줘"). 에이전트가 스스로 판단해
   연쇄 실행하지 않는다.
2. 행동이 **되돌릴 수 있다**(스크롤·포커스 이동·읽기 전용 내비게이션). 결제·삭제·
   설치·로그인·전송·보안 프롬프트는 **자동화 대상에서 제외** — 안내만 한다.
3. 대상이 **접근성 트리에서 명확히 식별**된다(레이블 있는 노드). 비전 좌표 추정만으로
   클릭하지 않는다 — grounding이 불확실하면 자동화 대신 안내로 강등.

플랫폼 무관 `Action` 타입과 `Automator` 추상 인터페이스는 코어(MIT)에 두되,
**허용 행동 집합을 좁게** 정의한다. 구체 어댑터(브라우저/UIA)는 이 좁은 집합만 구현.

### D. 그라운딩 (Grounding) — "그 버튼이 어디인가"
안내든 자동화든 대상을 특정해야 한다. **접근성 트리 우선**(UIA/AX/DOM, 정확·빠름·
비전 토큰 0), 트리가 부실하면 **비전은 안내에만** 쓰고 **자동 클릭에는 쓰지 않는다.**
비전 좌표는 "대략 화면 우측 상단"처럼 **사람에게 방향을 알려주는 용도**로는 유용하지만,
좌표 흔들림 때문에 **무인 클릭의 근거로는 부적합**하다(초안은 이를 폴백 실행 경로로
삼았는데, 이 사용자군에선 검증 불가 위험이라 자동 실행에서 배제).

### E. 확인·보고 (Verifier → Reporter)
초안의 "검증기(성공/실패 판정 후 자동 재계획)"를, **사용자에게 상태를 투명하게
보고**하는 역할로 재정의. `ChangeDetector`(이미 존재)로 "화면이 바뀌었다"를 감지하면,
**무엇이 바뀌어 보이는지 낭독**하고 판단을 사용자에게 돌려준다. 에이전트가 조용히
재시도를 누적하지 않는다(오류의 은폐 방지).

### F. 안전·신뢰
[ambient-copilot.md §3F](ambient-copilot.md)의 원칙을 유지·강화한다.

- **되돌릴 수 없는·보안 관련 행동은 자동화하지 않는다**(안내만): 결제·삭제·설치·
  로그인/개인정보 입력·외부 전송·보안 프롬프트(UAC/권한). 안내 시에도 "이 버튼은
  결제를 확정합니다"처럼 **결과를 먼저 경고**한다.
- **예고와 보고의 투명성**: 좁은 자동화를 하기 전에 말하고, 한 뒤에 말한다. 화면을 못
  보는 사용자의 유일한 검증 수단이므로 생략 불가.
- **프롬프트 인젝션 방어**: 화면 텍스트는 **데이터로만** 취급. 화면 속 "여기를
  클릭하세요"는 지시가 아니다. 행동 승인은 사용자 발화/키에서만 나온다.
- **스캠·보안 팝업**: `triage`가 이미 스캠/보안 프롬프트를 탐지하고
  `needs_confirmation`을 세운다(Epic A에서 스캠 분기 버그 수정). 이 위에서, 그런
  창은 **자동화 대상에서 원천 제외**한다.

### G. 오케스트레이터 (AdvisorLoop)
위 요소를 §2 안내 루프로 엮는다. 상태 기계는 "**사용자 입력 대기**"를 기본 상태로
두고, 자동화는 사용자 개시 이벤트로만 진입하는 분기다.

## 4. 코드 매핑: 재사용 vs 신규 (정정됨)

> ⚠️ **초안의 재사용 주장 정정.** 초안 §5는 `safety.apply_policy`가 "위험 행동 확인
> 게이트로 이미 존재하며 실행을 차단한다"고 적었으나 **사실과 다르다**:
> - 함수의 실제 위치는 `triage.apply_policy`이며, `safety` 모듈에 `apply_policy`는
>   없다(`safety`에는 분류를 상향 보정하는 `augment()`가 있다).
> - `triage.apply_policy`는 **들어오는 데스크톱 이벤트**(팝업/알림)를 분류해
>   `interrupt/queue/suppress`를 고르는 함수다. **나가는 행동을 심사하거나 차단하지
>   않는다.** `needs_confirmation` 플래그를 세우긴 하나(스캠·보안 프롬프트), 이는
>   행동 게이트가 아니라 "이 이벤트에 대한 대리 행동은 확인이 필요하다"는 표식이다.
> - 초안이 말한 "멈춰" **barge-in은 구현되어 있지 않다.** 현재 있는 것은 `SpeechBridge`의
>   음성 취소(발화 중단)뿐 — 진행 중인 행동을 중단하는 메커니즘이 아니다.

**그대로 재사용 (실제로 존재·유효):**
- `GoalTracker` — 의도 세션의 맥락 기반. ✅
- `NarrationEngine` — 화면 이해·안내 텍스트·상태 보고 낭독. ✅
- `ChangeDetector` — "화면이 바뀌었다" 감지(§E 보고 트리거). ✅
- `providers/*` — 안내 생성 LLM. ✅
- `triage`(스캠/보안 탐지 + `needs_confirmation`) — **자동화 제외 판단의 입력**으로
  참조. 단 이것은 이벤트 분류기이지 행동 게이트가 아니므로, **행동 게이트는 신규로
  만든다**(아래). ✅(용도 정정)
- 프로파일 speed 티어 / 다운스케일 — 지연·비용 레버. ✅

**신규 (`core/bitgil_core/agent/`):**
1. `intent.py` — `IntentSession`: 의도 수집·되묻기(자동 개시 없음).
2. `advisor.py` — 목표 + 화면 → **다음 한 수 안내**(초안 planner를 대체).
3. `automator.py` — `Action` 타입 + `Automator` 추상 인터페이스 + **행동 게이트**
   (되돌림 가능성·화이트리스트·사용자 개시 여부를 심사하는 신규 순수 함수. `triage`가
   아니라 여기서 나가는 행동을 막는다).
4. `grounding.py` — 대상 위치(트리 우선; 비전은 안내 전용).
5. `report.py` — 상태 보고(초안 verify의 재정의).
6. `loop.py` — `AdvisorLoop` 오케스트레이터.

**신규 (플랫폼 어댑터, 코어 밖):**
- 브라우저 어댑터(웹, 좁은 되돌림 가능 행동만) · Windows UIA 어댑터(실기기, 스텁 먼저).
- 음성 입력(STT): 웹 클라이언트에 `SpeechRecognition`(ko-KR) 추가 — 기존 TTS와 짝.
- **중단 제어**: "멈춰" 음성/키로 진행 중 자동화를 중단하는 메커니즘을 **신규 구현**
  (현재는 음성 취소만 존재하므로, barge-in은 만들어야 하는 항목).

## 5. 어디서 먼저 증명하나

Pi에서 테스트 가능한 곳은 **브라우저**다.
- 웹 클라이언트에 음성 입력 추가 → 기존 TTS와 대화 짝.
- **먼저 증명할 것은 자동화가 아니라 안내다**: "로그인 어떻게 해?" → 화면 읽고 →
  "우측 상단 '로그인' 버튼, Tab 3번 후 Enter" 안내 → 사용자가 실행 → 상태 보고.
- 좁은 자동화(사용자 개시·되돌림 가능·트리 식별)는 그다음, **읽기 전용 내비게이션**
  (스크롤·포커스 이동)부터 좁게 시작한다.

## 6. 열린 질문 / 리스크 (재검토 반영)

- **감독 불가 문제(핵심)**: 사용자가 오조작을 검증할 수 없다는 것이 자율 대행을 접은
  이유다. → 기본을 안내로, 자동화를 되돌림 가능·사용자 개시로 좁힘. 자율성 확대는
  [user-testing.md](user-testing.md)의 오류 탐지율 실험으로 **실증한 뒤에만**.
- **안내조차 틀릴 수 있다**: 안내 텍스트도 AI 생성물이라 50% 오류율의 지배를 받는다.
  → 화면에 실제 보이는 요소만 지목(반날조), 불확실하면 "확실치 않다"를 명시, 되돌릴 수
  없는 대상은 결과를 먼저 경고.
- **지연**: 접근성 트리 우선(비전 0), 진행 해설로 대기 체감 완화, speed 티어.
- **프롬프트 인젝션**: 화면 콘텐츠는 데이터로만. 승인은 사용자 의도에서만.
- **자율성의 경계**: 보호자 설정 + 보수적 기본값(화이트리스트 밖·되돌릴 수 없음 = 안내만).
